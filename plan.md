# План разработки библиотеки `dslparser`

## 1. Назначение и источники требований

Этот файл задаёт последовательный план разработки Go-библиотеки разбора DSL учебных сценариев.

Используй источники в следующем порядке приоритета:

1. [`tz.md`](./tz.md) — обязательное техническое задание и главный источник требований.
2. [`DSL v1.1.md`](./DSL%20v1.1.md) — спецификация синтаксиса и примеры DSL.
3. [`AGENTS.md`](./AGENTS.md) — постоянные правила работы Codex в репозитории.
4. Этот файл — границы, порядок и критерии этапов.

## 2. Как выполнять план

- Пользователь запускает работу указанием идентификатора этапа, например: `Выполни этап T06`.
- Выполняй только названный этап и его подзадачу проверки. Не начинай следующий этап без отдельного указания.
- Перед началом прочитай `tz.md`, `AGENTS.md`, описание выбранного этапа и фактические файлы, от которых он зависит.
- Не выполняй этап реализации `Ixx`, пока не завершён соответствующий тестовый этап `Txx`.
- В тестовом этапе сначала создай тесты, затем выполни указанную проверку RED. Не добавляй производственный код.
- В этапе реализации создай минимально достаточную законченную реализацию, затем выполни проверку GREEN. Не ослабляй уже принятые тесты.
- Каждая подзадача проверки является отдельной задачей внутри этапа и выполняется после создания или изменения файлов.
- Если проверка обнаружила дефект в пределах этапа, исправь его и повтори проверку до достижения критерия этапа.
- Если дефект относится к ранее завершённому этапу, исправь совместимость в текущем этапе и перечисли затронутые файлы. Не переписывай архитектуру без требования `tz.md`.
- После успешной проверки замени маркер этапа в этом файле с `[ ]` на `[x]`. Не отмечай этап выполненным до проверки.
- Не создавай функции, пакеты и расширения, предназначенные только для будущего этапа.

### Формат результата каждого этапа

Codex должен:

1. создать или изменить готовые файлы по указанным путям;
2. предоставить файлы целиком как скачиваемые артефакты, а не как блоки кода в сообщении;
3. кратко перечислить созданные и изменённые пути;
4. перечислить выполненные команды и их результат;
5. указать следующий допустимый этап;
6. явно сообщить о незавершённой проверке или блокере вместо объявления этапа завершённым.

Пути в плане указаны относительно корня модуля `dslparser/`. Файлы `tz.md`, `DSL v1.1.md`, `AGENTS.md` и `plan.md` должны находиться в корне репозитория рядом с каталогом модуля либо в корне самого модуля, если репозиторий содержит только этот модуль. Перед первым этапом зафиксируй фактический корень и далее не меняй его.

## 3. Правила проверочных подзадач

### Проверка после тестового этапа

1. Запусти `gofmt` для новых и изменённых `.go`-файлов тестов.
2. Проверь соответствие тестов требованиям `tz.md` и границам этапа.
3. Запусти целевой `go test`.
4. Зафиксируй RED: тест должен завершиться неуспешно только из-за отсутствующего или ещё не реализованного поведения этапа.
5. Устрани синтаксические ошибки, ошибочные импорты и сбои, не связанные с ожидаемо отсутствующей реализацией.
6. Если тест неожиданно проходит на заведомо отсутствующей функции, усили тест так, чтобы он проверял требуемый контракт.

На ранних этапах допустима ошибка компиляции из-за ещё отсутствующего идентификатора. Она должна быть прямо связана с будущей реализацией и не маскировать другие ошибки.

### Проверка после этапа реализации

1. Запусти `gofmt` для всего изменённого Go-кода.
2. Запусти целевые тесты этапа.
3. Запусти `go test ./...`.
4. Сверь реализацию с `tz.md`, уже созданным API и направлениями зависимостей.
5. Проверь, что исправление не ослабило тесты и не добавило обязанности будущих этапов.
6. Исправляй выявленные проблемы до GREEN.

`go test -race ./...`, `go vet ./...`, `go list ./...` и `go doc dslparser` обязательны в этапах, где они отдельно указаны, и в итоговой проверке.

## 4. Целевая структура модуля

```text
dslparser/
  go.mod
  doc.go
  parser.go
  document.go
  node.go
  element.go
  position.go
  diagnostic.go
  walk.go
  *_test.go
  testdata/
  README.md
  docs/
    architecture.md
    grammar-coverage.md
    diagnostics.md
    extending.md
  internal/
    model/
    normalize/
    registry/
    scan/
    structure/
    handlers/
```

`internal/model` содержит только изменяемые строительные структуры конвейера. Он нужен, чтобы внутренние пакеты не импортировали корневой пакет и не создавали циклические зависимости. Публичное дерево создаётся только при финальном замораживании результата.

**Цель:** создать минимальный каркас репозитория, необходимый для последующих тестовых этапов.

**Основная задача**

- Не создавай производственный код, тесты, CLI или документацию библиотеки.

**Отдельная задача проверки**

- Выполни `go env GOMOD` из каталога модуля и проверь, что выбран созданный `go.mod`.
- Выполни `go list -m` и ожидай ровно `dslparser`.
- Проверь отсутствие строк `require` и `replace`.

**Граница:** только модуль и расположение исходных документов.
