# ТЗ-инструкция: библиотека разбора DSL на Go

## 1. Роль и исходные данные

Реализуй библиотеку на Go для разбора DSL учебных сценариев, описанного в приложенном файле `DSL v1.2.md`.

Считай фактической версией приложенной спецификации DSL версию `1.1`. Название файла `DSL v1.2.md` ошибочно; заголовок спецификации и директива `@dsl-version 1.1` верны.

Перед написанием кода полностью изучи приложенную спецификацию. Используй её как источник правил DSL с учётом уточнений и приоритетов настоящего ТЗ. При расхождении требований применяй настоящее ТЗ.

Создай именно библиотеку. Не создавай CLI, сервер, редактор, валидатор содержания, интерпретатор, рендерер или готовое пользовательское приложение.

## 2. Цель

Библиотека должна:

1. принимать DSL-документ в UTF-8;
2. выполнять предварительную обработку строк;
3. распознавать синтаксические конструкции DSL с учётом контекста;
4. строить подробное дерево документа;
5. сохранять исходные данные после обязательного тримминга;
6. извлекать аргументы, диапазоны, логические области и доступную структурную информацию;
7. продолжать разбор после локальных синтаксических ошибок;
8. прикреплять ошибки разбора к соответствующим элементам дерева;
9. предоставлять потокобезопасный API только для чтения и обхода результата;
10. позволять точечно добавлять новые версии языка, теги и обработчики без переработки всего парсера.

Построй библиотеку так, чтобы поверх её результата можно было независимо реализовать расширенный валидатор, интерпретатор, транслятор или другой обработчик DSL.

## 3. Граница ответственности

### 3.1. Что обязан делать парсер

Выполняй только разбор и минимальные проверки, необходимые для однозначного построения дерева:

- проверяй корректность UTF-8;
- извлекай обязательную версию DSL;
- выбирай правила разбора по версии;
- классифицируй строки;
- распознавай заголовки, теги, аргументы и блочные границы;
- проверяй порядок открытия и закрытия фигурных блоков;
- учитывай экранирование при распознавании структурных символов;
- проверяй кавычки в тех схемах аргументов, где кавычки имеют синтаксическое значение;
- распознавай физическую и логическую вложенность;
- применяй контекстные правила, без которых невозможно определить принадлежность узла;
- извлекай однозначно определяемые внутренние части известных конструкций;
- выполняй восстановление после локальных ошибок;
- сохраняй диагностики в AST.

### 3.2. Что не должен делать парсер

Не реализуй в этой библиотеке:

- полный валидатор спецификации;
- проверку допустимого набора символов в именах тегов и ID;
- проверку уникальности ID;
- проверку уникальности имён вариантов;
- проверку обязательного количества заголовков и вариантов;
- проверку минимального количества элементов списков;
- проверку редакционных рекомендаций раздела 5 спецификации;
- проверку учебного смысла, связности или полноты материала;
- автоматическую проверку ответов;
- проверку путей к медиафайлам и поиск файлов;
- разбор HTML внутри `@text`;
- разбор таблиц внутри `@table`;
- исправление или нормализацию ошибочного DSL;
- обратную сериализацию AST в DSL;
- изменение AST после завершения разбора;
- систему пользовательских плагинов или подключаемых субпарсеров.

Отсутствующее обязательное значение известного тега сохрани как отсутствующее поле. Не считай его ошибкой парсинга, если структура строки и блока остаётся однозначной. Такие требования должен проверять внешний валидатор.

## 4. Фатальные и локальные ошибки

### 4.1. Фатальные ошибки

Не создавай `Document` и верни типизированную ошибку только в следующих случаях:

- вход содержит некорректный UTF-8;
- первая физическая строка после удаления BOM и тримминга не содержит корректную директиву `@dsl-version VERSION`;
- значение версии отсутствует;
- объявленная версия не поддерживается реестром;
- чтение из `io.Reader` завершилось ошибкой.

Не используй `panic` для ошибок входных данных.

### 4.2. Локальные ошибки

При любой иной ошибке продолжай разбор и возвращай частичный, пригодный для чтения `Document`.

Для каждой сохранённой строки или конструкции укажи, удалось ли разобрать её локально. При неудаче прикрепи к ближайшему подходящему узлу или элементу одну или несколько диагностик с:

- стабильным машинным кодом;
- кратким сообщением на русском языке;
- диапазоном ошибки;
- при необходимости диапазоном связанной конструкции, например открывающей скобки незакрытого блока.

Собери все локальные диагностики также в плоском списке документа в порядке исходного текста. Не дублируй одну ошибку несколькими диагностическими объектами: документ должен ссылаться на те же логические диагностики, что и узлы.

Локальная ошибка дочернего элемента не должна автоматически менять локальный статус корректно разобранного родителя. Незакрытый блок является собственной ошибкой открывающего его узла.

Используй минимум следующие стабильные коды. Дополняй каталог только при появлении самостоятельного условия ошибки:

| Код | Условие |
| --- | --- |
| `INVALID_UTF8` | вход не является корректным UTF-8 |
| `MISSING_VERSION` | первая физическая строка не содержит корректную директиву версии |
| `UNSUPPORTED_VERSION` | для объявленной версии отсутствует реестр |
| `READ_FAILURE` | ошибка чтения входного потока |
| `EMPTY_TAG_NAME` | после `@` отсутствует имя |
| `MALFORMED_HEADING` | нарушена базовая форма заголовка |
| `UNCLOSED_QUOTE` | не закрыта кавычка в токенизируемом аргументе |
| `INVALID_BLOCK_OPEN` | нарушена форма открытия фигурного блока |
| `ORPHAN_BLOCK_CLOSE` | закрывающая `}` не имеет открытого блока |
| `INVALID_BLOCK_CLOSE` | строка закрытия содержит лишние символы |
| `UNCLOSED_BLOCK` | для открытого блока не найдена закрывающая `}` |
| `UNSUPPORTED_TAG_FORM` | форма известного тега не поддерживается его записью реестра |
| `MISSING_SEPARATOR` | обязательный локальный разделитель отсутствует |
| `MULTIPLE_SEPARATORS` | найдено более одного допустимого локального разделителя |
| `STEP_OUTSIDE_TASK` | `@step` находится вне задания |
| `ENDTASK_WITHOUT_TASK` | `@endtask` не имеет открытого задания |
| `SPEAKING_CONTEXT` | `@speaking` не связан с допустимым предшествующим `@task` |
| `VARIANT_OUTSIDE_VARIANTS` | `@variant` находится вне `@variants` |
| `NESTED_VARIANTS` | обнаружен вложенный `@variants` |
| `CONTENT_BEFORE_VARIANT` | содержательный элемент находится до первой ветви `@variant` |

## 5. Публичный API

Размести публичный фасад в корневом пакете `dslparser`. Предоставь не менее следующих операций:

```go
func Parse(data []byte) (*Document, error)
func ParseString(source string) (*Document, error)
func ParseReader(r io.Reader) (*Document, error)
func Walk(document *Document, visit func(Cursor) bool)
```

Соблюдай следующие контракты:

- `Parse`, `ParseString` и `ParseReader` возвращают ненулевую ошибку только при фатальной ошибке;
- при локальных ошибках они возвращают документ и `nil`;
- `ParseReader` читает документ целиком в память и передаёт его тому же конвейеру, что и остальные функции;
- `Walk` выполняет детерминированный обход в порядке исходного документа;
- возврат `false` из `visit` запрещает вход в потомков текущего узла, но не прекращает обход соседних ветвей;
- `Cursor` содержит текущий узел, глубину и путь индексов от корня;
- контекст обхода вычисляется во время обхода и не хранится в виде указателей на родителей.

Добавь типизированную фатальную ошибку и экспортируемые значения или коды, позволяющие различать минимум:

- некорректный UTF-8;
- отсутствие или повреждение директивы версии;
- неподдерживаемую версию;
- ошибку чтения.

Не добавляй специализированные поисковые API по имени тега, ID, типу узла или диапазону. Для таких задач достаточно `Walk` и доступных полей узла.

## 6. Неизменяемость и потокобезопасность

Сделай `Document` и все возвращаемые через публичный API элементы AST неизменяемыми после завершения `Parse`.

- Не экспортируй изменяемые внутренние поля.
- Возвращай копии срезов из публичных методов доступа.
- Не возвращай карты, срезы или указатели, позволяющие изменить внутреннее состояние.
- Не добавляй публичные методы изменения, удаления или перемещения узлов.
- Не используй ленивые изменяемые кеши. Вычисляй индексы и производные данные во время разбора либо защищай неизбежную ленивую инициализацию стандартными средствами синхронизации.
- Не храни указатели на родителей.
- Обеспечь безопасное параллельное чтение одного документа и безопасные одновременные вызовы парсера из разных goroutine.
- Не используй изменяемое глобальное состояние. Реестр после инициализации должен быть неизменяемым.

## 7. Универсальная модель AST

Не создавай отдельный Go-тип для каждого DSL-тега и не строй иерархию интерфейсов тегов.

Используй компактную универсальную модель со следующими основными сущностями:

- `Document` — корневой объект;
- `Node` — универсальный узел документа;
- `Element` — универсальная разобранная часть узла;
- `BlockInfo` — сведения о фигурном блоке;
- `Position` и `Span` — координаты;
- `Diagnostic` — локальная ошибка разбора;
- `Cursor` — контекст обхода.

Используй целочисленные константы видов внутри `Node` и `Element`. Не вводи отдельные типы под каждый тег, аргумент, список или вариант.

### 7.1. Document

Храни в `Document`:

- объявленную версию в исходном и каноническом виде;
- диапазон строки `@dsl-version`;
- корневые узлы в порядке исходного документа;
- общий список диагностик;
- внутреннее неизменяемое хранилище, необходимое для работы методов доступа.

Директива версии является свойством документа. Не требуется дублировать её отдельным корневым узлом.

### 7.2. Node

Универсальный `Node` должен позволять получить:

- целочисленный вид узла;
- исходную строку после тримминга;
- разобранное значение, если оно создаётся обработчиком;
- исходное и каноническое имя тега;
- уровень заголовка;
- диапазон строки или логической области;
- локальный статус успешности разбора;
- локальные диагностики;
- разобранные `Element` в исходном порядке;
- дочерние `Node` в исходном порядке;
- сведения о блоке, если узел открывает фигурный блок;
- признак синтетической логической области.

Используй как минимум следующие виды узлов:

- логическая область шага;
- заголовок;
- тег;
- обычный текст;
- ошибочная попытка использовать блочную границу.

Последний вид является видом синтаксической конструкции, а не универсальным узлом «ошибка». Не создавай отдельную иерархию ошибочных узлов. Заголовок, тег или строка содержимого с ошибкой сохраняют собственный вид и получают отрицательный локальный статус.

### 7.3. Element

Используй `Element` для аргументов, полей, токенов, строк непрозрачного тела, разделителей и именованных групп.

`Element` должен позволять получить:

- целочисленный вид;
- стабильное техническое имя поля или группы;
- `Raw` — исходное значение после тримминга с сохранённым экранированием;
- `Value` — разобранное или декодированное значение, если оно необходимо обработчику;
- диапазон;
- локальный статус;
- диагностики;
- дочерние элементы в исходном порядке.

Не используй `map[string]any`, рефлексию или нетипизированные пользовательские данные. Для именованных групп применяй универсальные `Element` с дочерними элементами. Сохраняй порядок источника срезами, а не картами.

Используй единые технические имена элементов. Предусмотри минимум:

- `version`;
- `level`;
- `id`;
- `name`;
- `title`;
- `content`;
- `instruction`;
- `media_type`;
- `source`;
- `source_kind`;
- `body`;
- `items`;
- `before`;
- `after`;
- `upper`;
- `lower`;
- `positions`;
- `separator`.

Вынеси эти имена в константы, если они используются в нескольких обработчиках.

### 7.4. BlockInfo

Для блочного узла храни:

- диапазон открывающей `{`;
- диапазон закрывающей `}`, если она найдена;
- диапазон всего блока;
- признак наличия корректной закрывающей скобки;
- режим содержимого: структурный или непрозрачный.

Не создавай отдельные узлы для корректных открывающих и закрывающих фигурных скобок.

### 7.5. Линии и полнота данных

Каждая сохранённая содержательная строка должна быть представлена либо `Node`, либо строковым `Element` внутри своего блочного узла.

Для строк непрозрачного тела сохраняй:

- текст после тримминга;
- физический номер строки;
- диапазон;
- роль, если её однозначно назначил обработчик;
- локальный статус и диагностики.

Не сохраняй удалённые при тримминге символы, исходные отступы, тип перевода строк и наличие финального перевода строки.

## 8. Координаты

Определи координаты относительно текста строки после тримминга.

- Нумеруй физические строки с `1`.
- Нумеруй столбцы с `1` по Unicode-кодовым точкам, а не по байтам UTF-8.
- Представляй диапазоны полуоткрытым интервалом `[Start, End)`.
- Храни начальную и конечную позицию каждого распознанного тега, аргумента, заголовка, строки тела, разделителя и блока.
- Для синтетической логической области используй диапазон от первого до последнего принадлежащего ей исходного элемента.
- Для пустой сохранённой строки используй нулевую длину на соответствующем физическом номере строки.

Не пытайся восстановить столбцы относительно строки до тримминга.

## 9. Предварительная обработка входа

Выполни обработку строго в следующем порядке:

1. Прочитай весь вход.
2. Проверь корректность UTF-8 через стандартную библиотеку.
3. Если файл начинается с UTF-8 BOM, удали только BOM.
4. Раздели документ на физические строки с сохранением их номеров.
5. Удали в каждой строке все начальные и конечные Unicode-пробельные символы через `strings.TrimFunc(line, unicode.IsSpace)` или эквивалент на стандартной библиотеке.
6. Определи обязательную версию по первой физической строке.
7. Выбери реестр правил этой версии.
8. Передай нормализованные строки в дальнейший конвейер.

Применяй тримминг ко всем строкам без исключения, включая содержимое `@text`, `@table`, `@editor` и `@multifill`.

Сохраняй пустые строки только внутри `@text` и `@multifill`. В остальных контекстах учитывай их при определении соседства конструкций, после чего отбрасывай из AST.

Первая физическая строка обязана содержать `@dsl-version`. Не пропускай перед ней пустые строки или `@editor`.

## 10. Классификация строк

После тримминга классифицируй каждую строку с учётом текущего режима контейнера.

Различай:

- пустую строку;
- директиву версии;
- заголовок;
- строку тега;
- открытие блочной формы тега;
- корректную закрывающую границу;
- ошибочную попытку записать границу;
- обычный текст;
- непрозрачную строку тела.

В непрозрачном блоке не распознавай строки, начинающиеся с `@` или `#`, как DSL. Считай их сырым содержимым. Исключение — неэкранированная строка, состоящая только из `}`, которая закрывает текущий блок.

В структурном контейнере продолжай полный контекстный разбор вложенных DSL-конструкций.

## 11. Теги и аргументы

### 11.1. Распознавание имени

Считай строку тегом, если после тримминга её первый неэкранированный символ — `@`.

- Выделяй имя от `@` до первого Unicode-пробельного символа или структурного терминатора.
- Если имя отсутствует, создай узел тега с отрицательным статусом и диагностикой.
- Не проверяй допустимый алфавит имени.
- Не отклоняй неизвестное имя.
- Сохраняй исходный регистр имени в `Raw` и отдельном исходном поле.
- Для сопоставления с реестром приводи имя к нижнему регистру через стандартные средства Go.

### 11.2. Токенизация аргументной части

Всегда сохраняй полный сырой хвост строки после имени тега. Дополнительно токенизируй его по схеме обработчика.

- Разделяй токены Unicode-пробельными символами.
- Поддерживай двойные кавычки как механизм объединения значения с пробелами.
- Поддерживай `\"` внутри двойных кавычек и `\\` там, где обработчик снимает экранирование.
- Считай кавычки обычными символами в свободном текстовом хвосте, если схема тега не требует токенизации значения.
- При незакрытой кавычке в токенизируемом поле сохрани доступный текст, отметь поле и узел как локально неразобранные и добавь диагностику.
- Не добавляй поддержку одинарных кавычек, `key=value` или иных будущих форм, пока они не внесены в реестр новой версии.

Обработчик тега должен преобразовать универсальные токены в именованные `Element`, не теряя `Raw` и диапазоны.

### 11.3. Нормализация значений

- Сохраняй свободный текст, заголовки, названия, пути и контент в исходном регистре.
- Храни ID в двух представлениях: исходном и приведённом к нижнему регистру.
- Не выполняй Unicode-нормализацию NFC или NFKC.
- Приводи фиксированные имена тегов и перечислимые служебные значения к нижнему регистру только в разобранном `Value`; `Raw` не изменяй.
- Не проверяй уникальность или допустимый состав ID.

## 12. Экранирование

Сделай обработку экранирования небольшой общей функцией без отдельной подсистемы.

- Всегда сохраняй экранированную форму в `Raw`.
- Снимай одну экранирующую обратную косую черту только при создании разобранного `Value`, если конкретный обработчик использует это значение.
- Не снимай экранирование в сырых телах `@text`, `@table` и неизвестных блоков.
- Считай структурный символ экранированным, если непосредственно перед ним находится нечётное число последовательных обратных косых черт.
- Экранированные `@` и `#` в первой позиции не начинают тег или заголовок.
- Экранированная терминальная `{` не открывает блок.
- Экранированная отдельная `}` не закрывает блок.
- Обратную косую черту перед символом, не имеющим специального значения в текущем обработчике, сохраняй без ошибки.
- Обратную косую черту в конце строки сохраняй без ошибки, если она не образует незавершённую escape-последовательность, требуемую конкретной схемой.

Не реализуй контекстную семантику `;`, `|`, `<` и `>` в базовом парсере. Её должны обрабатывать будущие потребители соответствующих сырых блоков или специализированный обработчик, если он предусмотрен реестром.

## 13. Фигурные блоки и восстановление

### 13.1. Открытие блока

Считай тег блочным, если его строка заканчивается неэкранированной `{` и после неё отсутствуют символы после тримминга.

- Сохрани диапазон `{` в `BlockInfo`.
- Не считай отдельную строку `{` корректным открытием блока.
- Если после неэкранированной `{` присутствуют другие символы, сохрани строку как тег, не открывай блок и добавь локальную диагностику.
- Если известный тег не допускает обнаруженную форму по реестру, сохрани узел и его доступные данные, отметь локальную ошибку формы и продолжи разбор.

### 13.2. Закрытие блока

Считай корректной границей только неэкранированную строку, состоящую после тримминга строго из `}`.

- Присоедини корректную закрывающую границу к открытому блоку через `BlockInfo`.
- Не создавай для неё самостоятельный дочерний узел.
- Если закрывать нечего, создай самостоятельный узел попытки закрытия, отметь его как неразобранный и добавь диагностику лишней `}`. Продолжи со следующей строки.
- Если строка начинается с `}`, но содержит другие символы, не закрывай блок; сохрани ошибочную попытку границы с диагностикой.

### 13.3. Предварительный структурный проход

После классификации кандидатов и выбора версионного реестра, но до специальных обработчиков выполни отдельный контекстный проход по блочным границам.

Не ограничивайся сравнением общего количества `{` и `}`. Проверь порядок, стек открытых структурных блоков, режим каждого контейнера и экранирование.

Сформируй карту соответствий открывающих и закрывающих границ. Используй эту карту при построении AST; не ищи те же границы повторно в каждом обработчике.

Ошибка баланса не является фатальной и не запрещает последующий разбор.

### 13.4. Незакрытый блок

Если подходящая закрывающая `}` не найдена:

- сохрани узел блока;
- включи в него все последующие строки до конца файла с учётом режима тела;
- оставь закрывающий диапазон отсутствующим;
- отметь узел как локально неразобранный;
- добавь диагностику незакрытого блока;
- заверши доступный разбор его содержимого без аварийного завершения парсера.

Для непрозрачного блока первой подходящей границей является первая неэкранированная отдельная строка `}`. Не распознавай вложенные открывающие теги внутри его тела.

## 14. Реестр тегов и фабрика обработчиков

Создай единый неизменяемый машиночитаемый реестр. Сделай его единственным источником технических правил известных тегов.

Ключ реестра должен учитывать:

- версию DSL;
- каноническое имя тега.

Описание тега должно задавать только сведения, нужные парсеру:

- допустимые формы: однострочная, блочная или обе;
- схему аргументной части;
- режим тела: непрозрачное или структурное;
- идентификатор универсального обработчика аргументов;
- идентификатор специального обработчика аргументов, если нужен;
- идентификатор обработчика тела, если нужен;
- влияние на логический контекст и правила неявного завершения области;
- правила сохранения пустых строк;
- версию или диапазон версий правила.

Не помещай в реестр редакционные рекомендации, правила отображения и проверки, относящиеся к внешнему валидатору.

Создай фабрику обработчиков, которая по записи реестра собирает последовательность этапов для тега. Разреши следующие комбинации:

- только универсальный обработчик;
- только специальный обработчик;
- универсальный обработчик с последующей специальной детализацией;
- сырой непрозрачный блок без дополнительного разбора;
- структурный контейнер с рекурсивным разбором DSL.

Не делай реестр и фабрику публичной системой плагинов. Новая версия или тег добавляются изменением локальной записи реестра, обработчика и тестов библиотеки.

### 14.1. Неизвестные теги

Неизвестный тег является допустимым для базового синтаксического разбора.

- Создай обычный узел тега.
- Сохрани исходное и каноническое имя, сырой хвост, универсальные токены и позиции.
- Не добавляй диагностику только из-за неизвестного имени.
- Если строка заканчивается корректной `{`, считай тег неизвестным блочным тегом.
- Всегда считай тело неизвестного блочного тега непрозрачным.
- Сохрани строки такого тела без распознавания вложенных DSL-тегов.
- Если `{` отсутствует, считай неизвестный тег однострочным.

## 15. Режимы содержимого

Разделяй два независимых признака:

1. разрешён ли рекурсивный разбор DSL-тегов внутри тела;
2. нужен ли неглубокий специальный разбор сырых строк тела.

Все неструктурные блочные теги являются непрозрачными относительно DSL-вложенности. Строки `@...` и `#...` внутри них остаются содержимым.

Применяй три практических режима:

- `structural`: рекурсивно разбирай дочерние DSL-конструкции;
- `opaque-raw`: сохраняй строки без внутреннего разбора;
- `opaque-shaped`: не распознавай вложенный DSL, но разделяй строки на однозначные группы по правилам конкретного тега.

Для внешних субпарсеров не создавай интерфейс регистрации или вызова. Публичного доступа к `Raw`, строкам тела и их диапазонам достаточно.

## 16. Правила заголовков и шагов

### 16.1. Заголовки

Распознавай заголовок по одному или нескольким неэкранированным `#` в начале строки.

- Требуй хотя бы один Unicode-пробельный символ после маркера уровня.
- Сохраняй любое количество `#` как числовой уровень.
- Не ограничивай парсер уровнями 1–3.
- При отсутствии пробела или текста сохрани узел заголовка с отрицательным статусом и диагностикой.
- Не проверяй средствами парсера количество и допустимость уровней; это задача валидатора.

### 16.2. Логические шаги документа

Построй синтетические узлы логических шагов и помести в них исходные узлы в исходном порядке.

Реализуй правила спецификации 1.1:

- заголовок `###` начинает новый шаг;
- `@newpage` завершает текущий шаг и начинает новый шаг без собственного заголовка;
- шаг заканчивается перед следующими `###`, `@newpage` или концом файла;
- если `#`, необязательный `##` и первый `###` следуют без отображаемого материала между ними, создай один шаг, содержащий все эти заголовки;
- пустые строки и `@editor` не считаются отображаемым материалом и не нарушают указанную последовательность;
- если между `#`/`##` и первым `###` имеется обычный текст или отображаемый тег, создай предваряющий шаг с именем из `#`;
- если первой границей после `#` является `@newpage`, материал перед ней образует первый шаг;
- если нет ни `###`, ни `@newpage`, создай один шаг с именем из `#`;
- `@newpage` включи как технический узел в начинаемый им шаг;
- не проверяй пустоту шага и количество заголовков — оставь это валидатору.

Сохраняй синтетический шаг как универсальный `Node` с признаком логической области. Не создавай отдельный Go-тип шага.

## 17. Логические области задания, этапа и вариантов

### 17.1. `@task`

Используй узел `@task` как логический контейнер последующего материала.

Завершай его непосредственно перед:

- следующим `@task`;
- `@endtask`;
- `@header`;
- `@newpage`;
- `@variants`;
- заголовком `###`;
- концом файла;
- следующим `@variant` или закрытием родительского `@variants`, если задание находится в ветви.

Появление `@variants` одновременно завершает открытый `@step` и `@task` перед самим `@variants`.

Сохраняй исходный и приведённый к нижнему регистру ID как элементы узла. Не проверяй символы или уникальность ID.

### 17.2. `@endtask`

Если задание открыто, закрой текущий `@step`, включи `@endtask` в завершаемое задание и закрой задание. Если задания нет, сохрани `@endtask` в текущем контексте с диагностикой структурного контекста.

### 17.3. `@step`

Используй узел `@step` как логический контейнер внутри текущего `@task`.

- Следующий `@step` закрывает предыдущий.
- Любая конструкция, закрывающая `@task`, закрывает и текущий `@step`.
- Если активного задания нет, сохрани узел в текущем контексте с диагностикой.

### 17.4. `@speaking`

Связывай `@speaking` только с ближайшим непосредственно предшествующим `@task`. Между ними разрешай пустые строки и `@editor`. Любая другая структурная, контентная или интерактивная конструкция разрывает допустимое соседство. При нарушении сохрани узел и добавь контекстную диагностику.

### 17.5. `@variants` и `@variant`

- Разбирай `@variants` как структурный фигурный контейнер.
- До первого `@variant` сохраняй `@editor`; другой материал сохраняй с контекстной диагностикой.
- Используй каждый `@variant` как логический контейнер до следующего `@variant` или закрывающей `}` родительского блока.
- Если `@variant` находится вне `@variants`, сохрани его с контекстной диагностикой.
- Не разбирай вложенный `@variants` как допустимый структурный контейнер текущей версии; сохрани конструкцию и диагностику, не теряя её содержимое.
- Не проверяй количество ветвей, уникальность их имён и непустоту ветвей.
- Не проверяй запрет `#`, `##`, `###` или `@newpage` внутри вариантов как семантическое правило валидатора, но не позволяй таким конструкциям повредить физическое дерево `@variants`.

## 18. Реестр и обработка тегов DSL 1.1

| `@endtask` | однострочная | нет | нет | завершение задания |

| `@key` | блочная | необязательный свободный `title` | `opaque-raw` | сохранить непустые строки |

| `@alt` | однострочная и блочная | однострочный `content` | `opaque-raw` | сохранить непустые строки блока |
| `@question` | однострочная | свободный `content` | нет | сохранить полный текст вопроса |
| `@multifill` | однострочная и блочная | необязательная свободная `instruction` | `opaque-raw` | сохранить предзаполненные строки, включая пустые |
| `@choice` | блочная | необязательная свободная `instruction` | `opaque-shaped` | каждая непустая строка — элемент `items` |
| `@multichoice` | блочная | необязательная свободная `instruction` | `opaque-shaped` | каждая непустая строка — элемент `items` |
| `@matching` | блочная | необязательная свободная `instruction` | `opaque-shaped` | разделить строки на `upper` и `lower` по строке `---` |

Если у блочного тега есть однострочный аргумент перед `{`, не включай `{` в значение аргумента.

### 18.1. Локальные разделители

Для `@example`, `@matching` и расширенного `@ordering` распознавай разделителем только неэкранированную строку, равную `---` после тримминга.

- Сохраняй сам разделитель и его диапазон отдельным `Element`.
- Для `@example` допускай отсутствие разделителя; при наличии одного создай группы `before` и `after`.
- Для `@matching` отсутствие разделителя или несколько разделителей не позволяют полностью классифицировать тело: сохрани все строки в `body`, отметь узел локально неразобранным и добавь диагностику.
- Для `@ordering` отсутствие разделителя означает сокращённую форму; один разделитель — расширенную; несколько разделителей означают локальную ошибку с сохранением строк в `body`.
- Не проверяй количество элементов в полученных группах.

### 18.2. Плейсхолдер `_____`

Распознавай неэкранированную последовательность из пяти подчёркиваний как встроенный элемент только в тех строках, которые уже разбирает соответствующий обработчик.

- Сохраняй диапазон каждого плейсхолдера.
- Не изменяй исходную строку.
- Не исправляй другое количество подчёркиваний.
- Проверку того, является ли иное количество подчёркиваний ошибочной попыткой плейсхолдера, оставь внешнему валидатору.
- Не выполняй поиск плейсхолдеров внутри сырых тел `@text` и `@table`.

## 19. Связь физической и логической структуры

Построй одно основное дерево, а не две расходящиеся копии документа.

- Используй дочерние узлы фигурного тега для физической вложенности структурного контейнера.
- Используй дочерние узлы `@task`, `@step` и `@variant` для их логических областей.
- Используй синтетические узлы шага только там, где у шага нет естественного фигурного контейнера.
- Сохраняй исходный порядок всех узлов внутри каждого контейнера.
- Не дублируй один исходный узел в нескольких местах дерева.
- Не создавай обратные ссылки и циклы.
- Определяй полный диапазон контейнера по его строке открытия, содержимому и строке завершения.

## 20. Конвейер разбора

Реализуй этапы как независимые последовательные модули:

1. чтение входа;
2. проверка UTF-8 и удаление BOM;
3. разбиение на физические строки и Unicode-тримминг;
4. обязательное извлечение версии;
5. выбор неизменяемого версионного реестра;
6. предварительная классификация строк-кандидатов;
7. контекстный проход по фигурным границам и построение карты блоков;
8. построение базовых узлов и физической вложенности;
9. диспетчеризация тегов фабрикой;
10. универсальный разбор аргументов;
11. специальные обработчики аргументов и непрозрачных тел;
12. построение логических областей шагов, заданий, этапов и вариантов;
13. вычисление диапазонов и окончательных локальных статусов;
14. сбор диагностик документа;
15. замораживание результата для потокобезопасного чтения.

Не объединяй все этапы в один цикл или одну функцию. Передавай между этапами небольшие явно определённые структуры данных. Не допускай, чтобы специальный обработчик конкретного тега напрямую управлял всем парсером.

## 21. Структура Go-модуля

Создай модуль `dslparser` с директивой:

```go
go 1.26
```

Сохрани компактный публичный API в корневом пакете. Раздели внутреннюю реализацию по устойчивым обязанностям. Используй следующую структуру как целевую; объединяй два соседних внутренних пакета только при наличии реального циклического или искусственного разделения:

```text
dslparser/
  go.mod
  doc.go
  parser.go
  document.go
  node.go
  element.go
  position.go
  diagnostic.go
  walk.go
  README.md
  docs/
    architecture.md
    grammar-coverage.md
    diagnostics.md
    extending.md
  internal/
    normalize/
    registry/
    scan/
    structure/
    handlers/
```

Распределение ответственности:

- корневой пакет — публичный фасад и неизменяемые представления результата;
- `normalize` — UTF-8, BOM, строки и тримминг;
- `registry` — версионные описания тегов;
- `scan` — классификация, токены, кавычки и экранирование;
- `structure` — фигурные и логические области, восстановление после ошибок;
- `handlers` — небольшие универсальные и специальные обработчики известных тегов.

Не создавай подпакет на каждый тег. Группируй обработчики по одинаковому формату данных и ответственности.

Если неизменяемый публичный фасад требует внутренней модели, держи изменяемую модель построения в `internal` и создавай публичное read-only представление только после завершения конвейера. Не экспортируй строитель AST.

## 22. Требования и ограничения к коду

### 22.1. Общие требования

- Пиши строго идиоматический Go.
- Используй только стандартную библиотеку Go.
- Не добавляй внешние зависимости.
- Форматируй весь код через `gofmt`.
- Соблюдай простую направленную зависимость пакетов и не допускай циклических импортов.
- Не используй `unsafe`.
- Не используй рефлексию.
- Не используй `map[string]any` и нетипизированные контейнеры для AST.
- Не используй глобальное изменяемое состояние.
- Не перехватывай `panic` как штатный механизм обработки ошибочного DSL.
- Не выполняй файловые, сетевые или другие побочные операции во время разбора, кроме чтения переданного `io.Reader`.

### 22.2. Размер и ответственность функций

- Каждая функция должна выполнять одно конкретное действие.
- Предпочитай небольшие функции с явными входами и результатами.
- Считай функцию длиннее примерно 30 логических строк сигналом проверить смешение обязанностей.
- Разделяй длинную функцию, если части имеют самостоятельные имена, контракты или тестируемое поведение.
- Не дроби линейный алгоритм на бессодержательные однострочные обёртки только ради ограничения длины.
- Используй ранние возвраты и избегай глубокой вложенности условий.

### 22.3. Абстракции

- Не создавай интерфейс, если имеется только одна реализация и не требуется реальная граница замены.
- Для диспетчеризации обработчиков предпочитай именованные типы функций и таблицы регистрации.
- Используй обычные `int`, `string`, `bool` и срезы, если отдельный тип не обеспечивает проверяемый контракт.
- Вводи отдельные типы только для устойчивых понятий публичного API: документа, узла, элемента, позиции, диапазона, диагностики, блочной информации и курсора обхода.
- Не создавай наследование через интерфейсы для разных тегов.
- Не создавай фабрику объектов ради каждого простого значения; фабрика нужна только для выбора конвейера обработки тега по реестру.

### 22.4. Ошибки и состояние

- Возвращай ошибки идиоматично и добавляй контекст через стандартный пакет `fmt` с `%w`.
- Для локальных ошибок DSL используй диагностики AST, а не возвращаемый `error`.
- Не скрывай частичный результат из-за локальной ошибки.
- Не исправляй вход автоматически.
- Не смешивай состояние разных запусков парсера.
- Не изменяй уже завершённый узел на этапе публичного чтения.

### 22.5. Расширяемость

- Добавление тега существующей версии должно требовать локального изменения реестра, добавления или повторного использования обработчика и тестов.
- Добавление новой версии существующего тега не должно изменять обработчики других версий.
- Общие функции токенизации, блоков, списков и разделителей не копируй в обработчики тегов.
- Специальный обработчик не должен знать о несвязанных тегах.
- Правила неявного завершения логических областей держи декларативно либо в одном структурном модуле, а не размазывай по обработчикам.
